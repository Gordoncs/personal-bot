# 知识库 Agent 读写规范

适用于任何接入此仓库的 Agent。写入人是当前要求同步的人；维护人是负责飞书权限和表结构的人。

## 核心原则

1. 知识库保存已经确定的事实，未知信息如实说明，待确认内容不得当成事实。
2. 先读后写，按主字段去重。所有业务写入必须通过 `kb.py`。
3. 写入前列出新增、更新、跳过、待确认清单，获得写入人确认后才能 `apply --yes`。
4. 不删除表、字段或记录，不改名，不偷偷增加字段或单选选项。`init` 是唯一结构写入口，首次使用也需要先预览并确认。
5. 不把凭证、密码、验证码、证件号、API key 等敏感信息写进文件、知识库、日志、回复或提交记录。

## 首次使用：doctor → init

运行 `python3 knowledge-base/kb.py doctor`，检查三个环境变量 `FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_BITABLE_APP_TOKEN` 和读取权限。

缺少表或字段时，询问写入人的称呼及其他成员，再运行：

```sh
python3 knowledge-base/kb.py init --name 你的称呼
# 多人：在上面的命令追加 --member 成员乙 成员丙，或 --member 成员乙:writer
```

把表、字段、选项、成员清单展示给写入人；得到确认后用相同参数加 `--yes`。自动 ID 为 `m1`、`m2`，首位成员是默认使用者。重复运行只补缺，不覆盖已有成员、记录或结构。初始化写入一条「欢迎使用」示例。

只使用环境变量提供凭证；若写入人明确选择本地 env 文件，也可通过 `--env-file 路径` 加载，但不能把真实值写入仓库。不要运行旧的建表或迁移脚本。

## 固定模板

| 表 | 主字段 | 字段和选项 |
|---|---|---|
| 成员 | ID | ID、名称、别名（逗号分隔） |
| 资料 | 标题 | 标题、内容、分类（个人信息/工作/学习/生活/其他）、标签、来源、更新时间 |
| 联系人 | 姓名 | 姓名、关系（同事/客户/朋友/家人/合作方/其他）、公司/身份、联系方式、备注、更新时间 |
| 项目 | 名称 | 名称、状态（进行中/已完成/暂停/想法）、进展、下一步、更新时间 |
| 任务 | 编号 | 编号、标题、详情、负责人、创建人、状态（待办/进行中/已完成/受阻）、截止日期、备注、创建时间、更新时间 |
| 进度 | 成员 | 成员、日期、内容、记录时间 |
| 通知 | 收件人 | 收件人、发件人、内容、创建时间、送达时间、状态（待发送/已送达） |

所有人员字段都是单选，选项为成员的**名称**。所有时间字段都是日期类型。运行 `schema` 获取当前真实表结构，不要凭记忆猜字段名或选项。

## 日常同步流程

1. 从对话提取已确认的资料、联系人、项目进展、任务、进度；忽略闲聊、推测和废弃方案。
2. `kb.py schema [表名]` 对齐字段、主字段和选项；`kb.py find 成员` 对齐当前写入人的身份。
3. `kb.py find <表名> --key <主字段值>` 或 `--keyword <关键词>` 比对已有记录。同一名称有多个匹配就先问写入人。
4. 生成只含已确认事实的 changes.json，运行 `kb.py plan changes.json`。把计划展示给写入人，说明每个新增和更新；敏感内容不要放进 changes 文件。
5. 得到对本次清单的确认后，运行 `kb.py apply changes.json --yes`。超过 20 条操作要额外确认批量范围并加 `--allow-large`。
6. 汇报表、主字段值、record_id 和回读是否成功；失败后先重新读取，不盲目重试。apply 不是事务，前面的成功写入不会回滚。

以上命令的完整路径为 `python3 knowledge-base/kb.py`，在 knowledge-base 目录内可用 `python3 kb.py`。

## changes.json

```json
[
  {"op":"upsert","table":"资料","key":"阅读计划","fields":{"内容":"每周读一篇论文","分类":"学习"}},
  {"op":"upsert","table":"项目","key":"示例项目","fields":{"状态":"进行中","下一步":"周三整理资料"}},
  {"op":"create_task","fields":{"标题":"整理资料","负责人":"写入人名称","创建人":"写入人名称","截止日期":"2026-11-07"}},
  {"op":"update_task","id":"T-0001","fields":{"状态":"进行中"},"note":{"by":"写入人名称","text":"已开始整理"}},
  {"op":"progress","member":"写入人名称","date":"2026-11-02","text":"完成资料整理"},
  {"op":"notify","to":"另一成员名称","from":"写入人名称","text":"请查看更新后的资料"}
]
```

示例中的成员名称必须换成成员表实际名称。文本用字符串，数字用有限数字或可解析的数字字符串，单选必须是已有选项，日期用 `YYYY-MM-DD`，工具按北京时间转换。不能写入暂不支持的复杂字段类型。

## 系统表的保护规则

- **成员**：日常只读。通过 `init --name ... --member ...` 补成员及对应的人员选项；已有 ID 和名称不修改。
- **任务**：只能 `create_task` / `update_task`，自动编号、创建时间和更新时间。备注只能通过 `note` 追加，格式为 `<北京时间ISO> <成员名称>：<内容>`，每条 note 为单行文本。完成任务改状态，不删除。
- **进度**：只能 `progress`，相同成员、日期、内容会去重。
- **通知**：只能 `notify` 新增待发送记录。由收件人的 BOT 实例投递，只有发送成功才标记已送达；受微信 24 小时窗口限制。

Python 的 `create_task` 不自动添加通知。给别人派任务且确实需要提醒时，在同一计划另加一条 `notify`；给自己派任务不要加通知。微信 BOT 的任务工具已经自动通知，不重复发送。

## 知识表与身份

资料、联系人、项目和用户以后手动增加的其他表都可 `upsert`。系统四表禁止 upsert。有「更新时间」日期字段的表由工具自动填，没变化的记录跳过。更新状态字段用最新确定内容完整替换，不伪造空白字段。

用 `find 成员` 读取 ID、名称和逗号分隔的别名。把用户提到的 ID/名称/别名唯一映射到成员后，在人员单选、note.by、notify.from 填**名称**；创建人和发件人必须是当前写入人。找不到或有歧义就询问，不猜测。

用户想添加自定义表或字段、已有信息冲突、结构类型不符、主字段不符、权限不足时，停下并说明具体原因。用户可以在飞书手动维护自定义结构；不要用业务命令绕过校验。

权限错误时建议检查应用权限和发布状态，再到多维表格右上角「…」→「更多」→「添加文档应用」授予可编辑。doctor 不试写，不保证编辑权限一定已授予。
